## Hard-won facts

**Runtime and models**

- Ollama's **engine binary** (`AppData/Local/Programs/Ollama/lib/ollama/llama-server.exe`)
  is still required for `gemma4:e2b` and `e4b` — upstream llama.cpp cannot read
  their tensor layout (`expected 2012, got 601`; the file is intact, the
  *reader* is not). We run it as a process the Arbiter owns, so the **daemon**
  is irrelevant, but that file must survive an Ollama uninstall. The 12b and
  26b load on upstream and are unaffected.
- **The adapter-name trap.** `owned_provider()` must declare
  `"adapter": "openai-compatible"`, not `"openai"`. `adapter_of()` reads
  `adapter` before `type`, and only names in `LOCAL_CAPABLE_ADAPTERS` earn
  local classification. One wrong word made local seats classify as **cloud**,
  which meant the **egress gate sealed payloads bound for Friday's own local
  model** and the ledger showed `gemma4:12b · openai`.
- **The seat→port map is on disk** at `runtime/residency/endpoints.json`, and
  is health-checked before it is trusted. Without it, any process lacking an
  in-process Arbiter asks the dead daemon and raises "Ollama is not running"
  about a model answering two ports away.
- **The e-series channel format**:
  `<|tool_call>call:get_weather{city:Oslo}<tool_call|>`. Parsing must be
  **schema-aware** — values contain commas, so the only reliable boundary is a
  declared parameter name. And **thinking must be off for tool turns**
  (`chat_template_kwargs: {"enable_thinking": false}`) or the model closes its
  thought channel on an end-of-generation token before emitting the call.
- `gemma4:e2b` and `e4b` ship with **no embedded chat template**;
  `gguf_extract` borrows the 12b's. Without it llama-server falls back to
  ChatML and hands the seat a template with no tool definitions in it.
- **Compaction budgets against the seat's served context** via the residency
  plan, not `model_catalog` (which asks the stopped daemon and returns None,
  falling back to a 200,000 default while the seat serves 131,072).

**Measurements on this machine**

- Speed ladder: `e2b` 166 tok/s · `e4b` 100 · `12b` 49 · `26b` 22.
- `gemma4:26b` cold load **53.5 s** — a single question is ~70 % load time,
  which is the whole argument for the batching accumulator.
- KV is nearly free: 12b at 32768 → 7718 MiB, at 131072 → 7814 MiB.
  **96 MiB buys 4× the window.**
- Context overhead per turn: ~11,681 tokens of system prompt + ~8,118 of tool
  schemas ≈ **20k before the user types**.
- **Two calls per turn** is why the heartbeat showed a near-constant 42,654
  input tokens: (system + tools) × 2 passes + tool results.
- Image generation: **~93 s warm, ~186 s from a cold ComfyUI**, 1024×1024.
- Tool chains: **15/15** across e2b/e4b/12b on a dependent five-call task;
  **6/6 with the Ollama daemon fully stopped**.
- `--n-cpu-moe` best measured point is **18** (7973 MiB, fits the 8186 MiB
  lease budget). One run per candidate — a direction, not a settled number.

  Hit three times: `preferred_model`, `heavy_hitter`, `away_drain_after_s`. The
  API returns success and the value vanishes.

- Run pytest with `.\venv\Scripts\python.exe`, never bare `python`.
