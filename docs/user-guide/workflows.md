# Workflows

Workflows keep a useful procedure, its timing and its results together. Open
**Workflows**, use the link in a project, or ask Friday in chat or voice.

## Start with a result

Describe what you want, or choose a starter such as **Research brief**, **Daily
briefing**, **Watch for changes**, **Notes to document**, or **Specification to
reviewed change**. Choosing a starter fills a draft; saving and running are
separate actions.

In **Result and context**, choose the project and destination chat, identify
the sources, and describe the result and the checks that matter. Results can
be replies, editable documents, files, or code changes. Sources must already
be available to Friday; writing the name of a service does not connect it.

Run a first example, look at its result, and correct the procedure as needed.
Edits create new revisions. A run retains the revision it started with, even
if you edit the workflow while it is working. Friday rejects a save from an
older editor if another edit has already changed that revision.

## Follow the work

Each run has its own steps and result links. Use **Details** to open its task,
destination chat or exact document version. A saved document link never
substitutes a different document when the original is unavailable.

**Deliverable verified** means the expected output was found and checked
against the run's saved evidence. Quality requirements, such as whether an
argument is convincing or every requested source was covered, remain labeled
for review. A saved code change is not proof that its tests passed. Unchecked
output stays visibly distinct from verified output.

Execution and delivery have separate records. If delivery fails, use **Retry
delivery** to post the existing result again without rerunning its steps.
Repeating a run starts a new run;
it is not a way to establish whether an earlier external action happened.

## Make it a routine

Set a daily, weekly, interval or one-time schedule. Choose completion notices,
notices only when the result changes, or no completion notices. A change
monitor establishes a first baseline and retains it for later comparisons.
Failed source reads are not evidence that nothing changed.

**Pause** stops future scheduled starts. **Stop** requests cancellation of the
active run after its current tool finishes. A workflow continues when its
desktop screen is closed, while Friday's runtime remains running. The computer
must be awake and the required services and models available; this feature
does not provide an always-on remote host or mailbox/webhook event triggers.

## Reuse and correction

Use **Keep as reusable procedure** after reviewing a successful run to save its steps as
a reusable skill. Friday can retrieve the complete procedure when it is
relevant. Learning saves a procedure, not model training or new permissions.
Prior skill manifests remain in local history when a skill is replaced.

You can ask Friday to inspect a workflow's saved revisions or restore a prior
revision. Restoration creates another revision, keeping the intervening
history. Correct the saved workflow before the next run when a procedure
needs to change.

## Ask in chat or voice

Examples:

- “Show the steps and last result of my research brief.”
- “Turn these notes into an editable document in this project.”
- “Run that workflow, and tell me when the result is ready.”
- “Make it run every weekday at eight; only notify me about changes.”
- “Pause its schedule.” or “Stop the run that's working now.”
- “What can you do here, and what needs connecting first?”

Friday uses the same operations and permissions for these requests as the
desktop controls. Private data, file access and outward actions retain their
existing checks. A stored workflow or skill does not approve those actions.
